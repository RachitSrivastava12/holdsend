# 2026-11-20

## Done today

- Fixed issue [#54](https://github.com/zyakuhq/holdsend/issues/54) in [#84](https://github.com/zyakuhq/holdsend/pull/84) ([decision 0019](../docs/decisions/0019-schema-without-boot-locks.md)). `postgresSchema()` is meant to run when an app starts, but two of its statements locked the table even when they had nothing to do. So a server that restarted while a backup or a long transaction had the table open made every request with an idempotency key wait. Nothing was lost or sent twice, but requests were slow. First reproduced on Postgres 16: a claim waited more than a second behind the schema. Now:
  - The schema checks the catalog first and runs those statements only when something is missing.
  - An advisory lock lets two instances start at the same time. Before, one of them failed, and that was true before this change too.
  - Tests against a real Postgres fail on the old code and pass now. CI's Postgres job runs them.
- A separate agent reviewed the first version and found three problems: CI skipped the new test, two starting instances could race, and the README's lock-timeout advice could leave a pooled connection with the timeout. All three are fixed.
- `main` CI stayed green.

## LinkedIn post
A good bug report changes how you read your own code. Someone outside the team showed that our Postgres setup, which we told people to run every time their server starts, could make every write wait behind a backup. The statements were idempotent, so we had called them safe. But idempotent is not the same as free: Postgres locks the table before it checks whether there is anything to do. The lesson for me is that "safe to run twice" has to include what it blocks while it runs. Today's fix checks the catalog first and touches the table only when something is missing. Two servers that start at the same time now wait for each other instead of one failing. Tests against a real Postgres prove the old version blocked and the new one does not. https://github.com/zyakuhq/holdsend
